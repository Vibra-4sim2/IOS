# Rapport de Soutenance – Application iOS VIBRA

## 1️⃣ Présentation générale de l’application iOS

### Objectif de l’application
L’application VIBRA est une application mobile native iOS permettant aux utilisateurs d’organiser, rejoindre et gérer des sorties (balades, randonnées, événements communautaires), d’échanger des messages privés ou de groupe, de recevoir des notifications, et d’interagir avec une communauté. Elle vise à faciliter la création de liens sociaux autour d’activités partagées.

### Rôle du front iOS par rapport au back-end
L’application iOS constitue l’interface utilisateur (front-end) : elle permet à l’utilisateur d’interagir avec les fonctionnalités offertes par le back-end (serveur). Le front-end gère l’affichage, la navigation, la saisie utilisateur, et la synchronisation des données avec le back-end via des API REST.

### Type d’application
- Application mobile native iOS
- Développée en Swift
- Utilise principalement le framework SwiftUI pour l’interface utilisateur

### Frameworks principaux utilisés
- **SwiftUI** : Framework Apple pour construire des interfaces utilisateur déclaratives et réactives.
- **Combine** : Pour la gestion des données asynchrones et la synchronisation UI/données.
- **Foundation** : Pour la gestion des données, du réseau, etc.

#### Qu’est-ce qu’une application iOS ?
Une application iOS est un programme conçu pour fonctionner sur les appareils Apple (iPhone, iPad). Elle est développée en Swift (ou Objective-C) et utilise des frameworks Apple (UIKit, SwiftUI) pour l’interface et la gestion du cycle de vie. Elle interagit avec le système d’exploitation pour afficher des écrans, gérer les interactions, accéder au réseau, etc.

## 2️⃣ Architecture iOS utilisée (PARTIE CRITIQUE)

### Architecture choisie : MVVM (Model-View-ViewModel)

#### Pourquoi ce choix ?
- **Séparation claire des responsabilités** : UI, logique métier, accès aux données sont séparés.
- **Facilite la maintenance** : chaque couche a un rôle précis, le code est plus lisible et testable.
- **Adapté à SwiftUI** : MVVM permet de lier facilement les données à l’UI grâce à l’observation.

#### Problèmes résolus
- **Éviter le code spaghetti** : la logique métier n’est pas mélangée à l’UI.
- **Réutilisabilité** : les ViewModels peuvent être testés et réutilisés indépendamment de l’UI.

#### Avantages pour la maintenance et l’évolution
- **Ajout de fonctionnalités facilité**
- **Correction de bugs localisée**
- **Tests unitaires sur la logique métier**

### Schéma de circulation des données

```
UI (View) → ViewModel → Service → API → Back-End
```
- **UI (View)** : Affiche les données, reçoit les actions utilisateur.
- **ViewModel** : Gère l’état, la logique métier, expose les données à la vue.
- **Service** : Gère les appels réseau, la persistance locale.
- **API** : Interface de communication avec le back-end.
- **Back-End** : Source des données distantes.

#### Rôle de chaque couche
- **View** : Affichage, interactions utilisateur.
- **ViewModel** : Prépare les données pour la vue, gère l’état, observe les changements.
- **Service** : Effectue les requêtes réseau, traite les réponses, gère les erreurs.

## 3️⃣ Concepts fondamentaux iOS (EXPLIQUER COMME À UN DÉBUTANT)

### ViewController / View
- **ViewController** (UIKit) : Contrôleur qui gère un écran, reçoit les événements, met à jour la vue.
- **View** (SwiftUI) : Structure déclarative qui décrit l’interface utilisateur. Chaque écran est une View.

### Storyboard / SwiftUI View
- **Storyboard** : Outil graphique pour construire l’UI (non utilisé ici).
- **SwiftUI View** : Code Swift qui décrit l’UI de façon déclarative et réactive.

### Navigation (NavigationController / TabBar)
- **NavigationStack** : Permet de naviguer entre des écrans (pousser/poper des vues).
- **TabBar** : Barre d’onglets en bas de l’écran pour accéder rapidement aux sections principales.

### Cycle de vie d’une vue
- **onAppear** : Appelé quand la vue apparaît à l’écran.
- **onDisappear** : Appelé quand la vue disparaît.

### Delegation / Closure / Observable
- **Delegation** : Permet à une classe de déléguer une action à une autre (peu utilisé en SwiftUI).
- **Closure** : Bloc de code passé en paramètre pour exécuter une action (ex : callbacks).
- **ObservableObject / @Published** : Permet de notifier la vue quand les données changent (pattern d’observation).

### State management
- **@State** : Variable d’état locale à la vue.
- **@StateObject / @ObservedObject** : Pour observer un ViewModel ou un objet partagé.
- **@EnvironmentObject** : Pour partager un ViewModel entre plusieurs vues.

## 6️⃣ Consommation des API (TRÈS IMPORTANT)

### Étapes détaillées :
1. **Appel d’une API REST** : Le ViewModel appelle un Service (ex : AuthService) pour effectuer une requête HTTP.
2. **Classe responsable** : Les classes dans le dossier Services (ex : AuthService, ChatService).
3. **Construction de la requête** : Création d’un objet URLRequest avec l’URL, la méthode (GET, POST), les headers (dont le token d’authentification).
4. **Gestion des réponses** : Le Service reçoit la réponse, vérifie le code HTTP, parse le JSON.
5. **Gestion des erreurs** : Si erreur réseau ou code HTTP inattendu, le Service renvoie une erreur au ViewModel.
6. **Parsing JSON** : Utilisation de Codable pour transformer le JSON en objets Swift.
7. **Mise à jour de l’UI** : Le ViewModel publie les nouvelles données, la vue se met à jour automatiquement.

---

## 7️⃣ Gestion de l’état & données
- **Stockage temporaire** : Les ViewModels stockent les données en mémoire.
- **Synchronisation UI/données** : Grâce à @Published et ObservableObject, l’UI se met à jour dès que les données changent.
- **Gestion du loading/erreur** : Les ViewModels exposent des états (isLoading, error) pour afficher des écrans de chargement ou d’erreur.
- **Gestion du token** : Le token d’authentification est stocké de façon sécurisée dans le Keychain.

---

## 8️⃣ Sécurité côté iOS
- **Stockage sécurisé** : Utilisation du Keychain pour stocker le token JWT.
- **Protection des données sensibles** : Jamais stockées en clair, accès restreint.
- **Bonnes pratiques** : Suppression du token à la déconnexion, pas de logs de données sensibles.

# Liste détaillée des écrans de l’application

## 1. HomeView
1. **Objectif** : Accueil, suggestions de sorties.
2. **Fonctionnalité métier** : Découverte de sorties, suggestions personnalisées.
3. **Données affichées** : Liste de sorties, recommandations.
4. **Origine des données** : API via HomeService.
5. **Classes impliquées** : HomeView, HomeViewModel, HomeService.
6. **Flux utilisateur** : Lancement → affichage suggestions → sélection d’une sortie.
7. **Interactions** : Sélectionner une sortie, accéder au détail.
8. **Cas d’erreur** : Erreur réseau, affichage d’un message.
9. **À l’oral** : « L’écran d’accueil propose des suggestions personnalisées de sorties, récupérées dynamiquement via l’API. »

### A️⃣ Déclencheur technique
- L’affichage de la liste est déclenché par l’événement `.task` de SwiftUI dans le body de HomeView. Cet événement exécute `await viewModel.load()` dès que la vue apparaît à l’écran.
- L’utilisateur peut aussi déclencher un rechargement via des filtres ou un changement d’onglet (modification de propriétés observées).

### B️⃣ Flux code détaillé
1. L’événement `.task` appelle la fonction asynchrone `load()` du HomeViewModel.
2. `HomeViewModel` (annoté `@StateObject` dans la vue) exécute `load()`, qui appelle le service réseau `HomeService.shared.fetchRidesWithCreators()`.
3. Lorsque la réponse arrive, la propriété `@Published var items: [RideWithCreator]` du ViewModel est modifiée.
4. Grâce à l’annotation `@Published`, SwiftUI observe automatiquement les changements de cette propriété via Combine.
5. Quand `items` change, SwiftUI déclenche un nouveau calcul du body de la vue (reconstruction de la vue), ce qui met à jour l’affichage de la liste.

### C️⃣ Rôle précis de SwiftUI
- La View est une `struct` car SwiftUI utilise la valeur et la composition pour optimiser le rendu et permettre la reconstruction rapide de l’UI.
- Le body est recalculé à chaque changement d’état observé (ici, `items`, `isLoading`, `errorMessage`).
- SwiftUI optimise le rendu en ne réaffichant que les sous-vues dont les données ont changé (diffing algorithm).

### D️⃣ Combine (utilisé en interne)
- Le property wrapper `@Published` crée un Publisher pour chaque propriété annotée.
- SwiftUI souscrit automatiquement à ces Publishers via l’observation de l’ObservableObject.
- Les modifications sont propagées sur le thread principal (`@MainActor`).
- Les erreurs réseau sont capturées dans `errorMessage` (également `@Published`), ce qui permet d’afficher dynamiquement un état d’erreur.

### E️⃣ Justification technique
- Cette implémentation respecte MVVM : la vue ne connaît que le ViewModel, qui encapsule toute la logique métier et l’accès aux données.
- Le ViewModel expose uniquement des propriétés observables, la vue ne fait que les consommer.
- Un mauvais design consisterait à faire les appels réseau directement dans la vue, ce qui rendrait le code non testable, difficile à maintenir et fragile face aux évolutions.

### F️⃣ Phrase ORALE À DIRE AU JURY
« Sur HomeView, chaque chargement de données est déclenché par l’événement .task, qui appelle une fonction asynchrone du ViewModel. Dès que la propriété @Published items change, SwiftUI le détecte via Combine et reconstruit automatiquement la vue, garantissant une synchronisation parfaite entre l’état du modèle et l’interface. »

- Le chargement des favoris est déclenché par `.onAppear` ou `.task` dans SavedRidesView. L’utilisateur peut aussi déclencher un ajout/retrait de favori via un bouton.

### B️⃣ Flux code détaillé
1. L’événement `.onAppear` ou `.task` appelle la fonction asynchrone `loadSavedRides()` du ViewModel ou du SavedRidesManager.
2. Le ViewModel (annoté `@StateObject` ou `@ObservedObject`) exécute `loadSavedRides()`, qui récupère les favoris localement ou via HomeService.
3. À la réception, la propriété `@Published var savedRides: [RideWithCreator]` du ViewModel est modifiée.
4. Grâce à `@Published`, SwiftUI observe ce changement via Combine.
5. Quand `savedRides` change, SwiftUI recalcule le body de la vue, mettant à jour la liste affichée.

### C️⃣ Rôle précis de SwiftUI
- La vue est une `struct` pour permettre la composition et la reconstruction rapide.
- Le body est recalculé à chaque changement d’état observé (ici, `savedRides`, `isLoading`, `errorMessage`).
- SwiftUI optimise le rendu en ne mettant à jour que les sous-vues concernées.

### D️⃣ Combine (utilisé en interne)
- `@Published` crée un Publisher pour chaque propriété annotée.
- SwiftUI souscrit automatiquement à ces Publishers.
- Les modifications sont propagées sur le thread principal (`@MainActor`).
- Les erreurs réseau ou de synchronisation sont capturées dans `errorMessage` (également `@Published`).

### E️⃣ Justification technique
- Cette implémentation respecte MVVM : la vue ne gère que l’affichage, le ViewModel encapsule la logique métier et l’accès aux données.
- Un mauvais design consisterait à faire les accès favoris dans la vue, rendant le code non testable et difficile à maintenir.

### F️⃣ Phrase ORALE À DIRE AU JURY
« Sur SavedRidesView, chaque modification des favoris est propagée via @Published, ce qui permet à SwiftUI de reconstruire la vue et d’assurer la cohérence entre l’état local et l’interface. »
